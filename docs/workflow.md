# Workflow проекта

Данный документ описывает общий рабочий процесс AI-модуля ОРИКС.

Проект анализирует данные по операционным рискам банка, выполняет детерминированные расчёты на Python и формирует аналитический вывод с помощью LLM.

## Общая схема работы

```text
Input JSON
↓
InputValidator
↓
AnalysisPipeline
↓
Deterministic Calculator
↓
MetricCalculations
↓
PromptBuilder
↓
LLM
↓
Validator / Evaluator
↓
Final analytical result
```

## 1. Input JSON

На первом этапе пользователь передаёт входные данные в формате JSON.

В данных указываются:

* тип метрики;
* отчётный период;
* значения Моего банка;
* значения рынка / кластера / банков-аналогов;
* дополнительные параметры, например репрезентативность.

## 2. Валидация данных

После получения JSON данные проходят проверку через `InputValidator`.

Валидация нужна для того, чтобы убедиться, что:

* все обязательные поля присутствуют;
* значения имеют правильный тип;
* числовые показатели действительно являются числами;
* структура данных подходит для выбранной метрики.

Если данные некорректные, расчёт не выполняется.

## 3. AnalysisPipeline

`AnalysisPipeline` управляет общим процессом обработки данных.

Он получает запрос, определяет тип метрики и выбирает нужный калькулятор.

Например:

* для метрики 1 используется калькулятор чистых потерь к бизнес-индикатору;
* для метрики 3 используется калькулятор распределения по бакетам;
* для метрики 5 используется калькулятор источников риска.

## 4. Детерминированный калькулятор

Каждая метрика имеет отдельный Python-калькулятор.

Калькулятор выполняет только точные расчёты:

* считает отклонения;
* сравнивает банк с рынком;
* определяет сценарий;
* находит ключевые значения;
* подготавливает дополнительные аналитические признаки.

LLM на этом этапе не используется.

## 5. MetricCalculations

После расчёта калькулятор возвращает результат в едином формате `MetricCalculations`.

В этот объект входят:

* тип метрики;
* период;
* значение Моего банка;
* среднее значение рынка / кластера;
* процент отклонения;
* итоговый сценарий;
* дополнительные поля `extra`.

Это позволяет всем метрикам работать в единой архитектуре.

## 6. PromptBuilder

`PromptBuilder` получает рассчитанные значения и формирует промпт для LLM.

В промпт передаются уже готовые факты:

* числовые значения;
* сценарий;
* отклонения;
* готовые предложения;
* ограничения по стилю.

Это нужно, чтобы LLM не придумывала расчёты самостоятельно.

## 7. LLM

LLM используется только для оформления аналитического текста.

Она не должна:

* считать проценты;
* выбирать сценарий;
* менять числовые значения;
* придумывать новые факты.

LLM получает готовые данные от Python и формирует связный аналитический вывод на русском языке.

## 8. Validator / Evaluator

После генерации текста результат проверяется валидатором или evaluator.

Проверка нужна, чтобы убедиться, что:

* текст не противоречит расчётам;
* сценарий сохранён правильно;
* числа не искажены;
* вывод написан в деловом стиле.

## 9. Final analytical result

На последнем этапе пользователь получает финальный аналитический вывод.

Этот вывод основан на точных расчётах Python и оформлен LLM в понятном бизнес-стиле.

## Главный принцип проекта

Главный принцип проекта — разделение расчётов и генерации текста.

Python отвечает за:

* математику;
* сценарии;
* проверки;
* подготовку фактов.

LLM отвечает за:

* стиль;
* связность текста;
* финальную формулировку вывода.

Такой подход снижает риск ошибок и галлюцинаций.
